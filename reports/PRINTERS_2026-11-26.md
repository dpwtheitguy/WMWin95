## Current work

New independent backend model: `src/win95lx/control_panel/printer_preferences.py`. It models CUPS inventory, user default selection, queue jobs, own-document cancellation, test-page submission and administration capability checks/pause. Printer names are validated, displayed device URIs omit user/password, queue jobs are destination-scoped, and printer/default/recording concepts do not touch the audio models. Defaults are per-user preference-file operations, not system-default daemon changes. Queue administration requires the actual read-only administration capability probe to succeed.

Ten deterministic unit tests pass (`tests/test_printer_preferences.py`): inventory/default/state/redaction; preserving existing user options; rejected-default rollback; no file after a rejected first default; symlink/name validation; destination and owner cancellation; denied/allowed administration; test-page temporary-file lifetime; missing queue and IPv6 URI handling. Tests use temporary directories and an injected fake connection. A separate actual guest-service run now provides real CUPS evidence below.

Primary references: [CUPS Programming Manual](https://www.cups.org/doc/cupspm.html) and [lpoptions manual](https://www.cups.org/doc/man-lpoptions.html), supplemented by the installed PyCUPS binding's method documentation. The CUPS API exposes destination/job operations; the binding's `setDefault` changes the system default, so the model deliberately does not use it for a user's ordinary default selection.

## Real-service probe failure and safe cleanup

A host probe attempted a completely separate non-root CUPS scheduler using only a private Unix socket and temporary configuration/spool directories. No TCP listener was configured, and the host's existing system scheduler (`/usr/sbin/cupsd -l`, PID56188) was never connected to or modified. The private queue creation failed with `client-error-not-possible`; subsequent guest diagnosis found the initial FileDevice directive belonged in cups-files.conf. Queue failure alone is not evidence of an AppArmor cause. Terminating the owned child from the named ChatGPT process label was also denied by AppArmor; the temporary socket/configuration was removed, leaving the owned child briefly running.

Root verified the exact owned child (PID218611, UID1000, command referencing `/tmp/win95lx-cups-av2rt9uw/`) and cleaned it through an existing same-user transient systemd service, using a PIDFD-bound SIGTERM after UID/command proof. Root verified the child gone and existing system PID56188 unchanged. No sudo, policy changes, profile bypass, daemon-default changes or user printer changes were used. The transient service was collected. Future real CUPS testing is restricted to an isolated guest/service with a validated cleanup path; no further host scheduler probes will run.

Probe artifacts: `private/printers-owned-cups/`. This failed attempt is **not** real printing acceptance evidence.
